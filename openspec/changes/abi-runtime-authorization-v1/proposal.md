## Why

Оператор должен запускать BBB обычным Deploy и позднее авторизовать работающий ABI. Новая авторизация не должна управлять торговым журналом или зависеть от его готовности. Существующие торговые сервисы и восстановление сохраняются.

## What Changes

- Единственный внутренний AuthorizationService владеет кандидатом, подтверждённой парой и состоянием авторизации. Он получает verifier и не знает о Bybit, журнале, Runtime, readiness и observers.
- REST получает подтверждённую пару только через узкий CredentialsSource. Подписанный GET использует одну пару на запрос с retry, POST не повторяется; публичные запросы доступны без авторизации.
- Следующий отдельный шаг: реальный ограниченный verifier credentials/UID/прав и защищённая доставка через age и Unix socket. Торговый журнал на этом шаге не меняется.
- После отдельного ревью composition root соединяет авторизацию с существующими компонентами. Только здесь выполняется минимально необходимое отделение локального восстановления от биржевой проверки; отдельного этапа переработки replay нет.
- Единый механизм допуска проверяет авторизацию для account API и дополнительно готовность торгового состояния для торговых циклов. Типизированный 503 означает гарантированный отказ до исполнения.
- Обычный deploy запускает существующий abi без пароля; авторизация выполняется позже. Старого env-режима или fallback в новой совокупной версии нет. Откат — прежний образ и его конфигурация.

## Capabilities

### New Capabilities

- `runtime-authorization` — независимая авторизация Bybit, защищённая поздняя доставка и безопасный допуск операций.

### Modified Capabilities

- `container-runtime` — разделение liveness и execution readiness, обычный deploy.
- `abi-entry-package-api` — типизированный отказ до исполнения.
- `abi-open-position-lookup-api` — типизированная временная неготовность.
- `abi-entry-cycle-recovery-api` — типизированная временная неготовность.
- `abi-position-management-api` — типизированный отказ до исполнения.

## Impact

Новая функциональность начинается от main, без кода PR #51. PR #52 сохраняет независимый AuthorizationService, draft PR #53 — адаптацию REST. Промежуточный #53 не сливается в main до работоспособной интеграции composition root. PR #49 — технический справочник по age, Runtime #46 сохраняется. bbb_stack #103 должен отказаться от интерактивного деплоя.

Формат журнала, расчёт позиции, семантика ордеров, торговая логика, mutex и существующий reconciliation не меняются. Сохраняются dry-run и ограничения liveTradingEnabled/Demo/Mainnet. Переход и интеграционный smoke разрешаются отдельно только на Demo; Mainnet запрещён.

Спек не является разрешением Apply. Каждый следующий содержательный шаг отдельно рассматривается и принимается.
