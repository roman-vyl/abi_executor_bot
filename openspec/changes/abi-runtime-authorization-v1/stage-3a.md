# Шаг 3A: локальное восстановление и проверка привязок

Статус: проект для ревью. Apply, merge и deploy не разрешены. Это узкий следующий шаг общего abi-runtime-authorization-v1, а не новая реализация авторизации.

## Context

В main функция replayCorrelationStore() последовательно выполняет replay(), closeLeftoverAdmissionIntents(), assureConfiguredActiveBindings() и выставляет EntryPackageReadiness. Последний хранит только изменяемый boolean и причину ошибки. Для будущей поздней авторизации нужен сохраняемый результат локальной фазы, который биржевая проверка не может перезаписать.

## Goals / Non-Goals

3A выделяет две фазы, сохраняя порядок и внешнее поведение текущего запуска. Не подключает AuthorizationService, verifier, age, Unix socket, REST credentials, private WS или новые observers. Не меняет маршруты, HTTP-контракты, live guard, shutdown, Runtime, Docker, формат журнала, расчёт позиции и семантику исполнения.

Сохранение существующего env-запуска здесь относится к неизменённому main, а не к поддержке env-fallback в будущей версии авторизации. В будущей совокупной версии Trading READY дополнительно требует AUTHORIZED; 3A не вводит и не имитирует этот факт.

## Decisions

### Две фазы и явные результаты

Предлагаемые внутренние контракты (имена уточняются при реализации без изменения границ):

```ts
type LocalRecoveryResult = Readonly<
  { ok: true } | { ok: false; reason: string }
>;
type BindingVerificationResult = Readonly<
  { ok: true } | { ok: false; reason: string }
>;
```

Локальная функция принимает только CorrelationReplayer и возвращает окончательный результат после replay() и закрытия оставшихся admission intents. У неё нет Bybit, credentials, readiness или callback запуска торговых компонентов. Успех одного replay() ещё не является успехом всей локальной фазы. Результат сохраняется в памяти процесса; новый durable формат не вводится.

Биржевая функция использует сохранённый LocalRecoveryResult и существующую assureConfiguredActiveBindings(). При неуспешном локальном результате немедленно возвращает отказ с исходной причиной, не читает активные записи и не обращается к Bybit. Она не получает repository.replay или closeLeftoverAdmissionIntents и не может повторить локальную фазу. Активные записи считываются для каждой разрешённой проверки, а не сохраняются как устаревающий снимок при replay.

Ни одна фаза сама не вызывает markReady(). Существующий replayCorrelationStore() остаётся тонкой последовательной обёрткой для нынешнего server.ts: сохраняет локальный результат, при успехе выполняет проверку привязок, публикует readiness только по совокупному результату. Существующий EntryPackageReadiness сохраняется без универсального lifecycle manager. Повтор биржевой фазы принимает тот же локальный результат и не запускает обёртку заново.

```text
replay → closeLeftoverAdmissionIntents → localRecoveryResult
                                            │
                              failure ──────┴──→ not ready
                                            │ success
                                  проверка привязок
                                            │
                              failure ──────┴──→ not ready
                                            │ success
                                          ready
```

Промежуточные и failed результаты не устанавливают ready. Предыдущая ошибка не может быть скрыта последующим успешным callback. Для 3A сохраняется последовательный запуск; автоматический scheduler, новая политика retry и поддержка конкурентных проверок не добавляются. Проверяется возможность отдельно повторить биржевую фазу после завершившегося отказа.

### Сохранение действующего поведения

Production server.ts продолжает вызывать существующую обёртку с нынешними аргументами. Проверки policy compatibility, legacy records, one-way и hedge остаются в assureConfiguredActiveBindings() с прежней семантикой. Никакие новые биржевые операции не добавляются. Пустой hedge и прежний one-way путь сохраняют отсутствие ненужных биржевых запросов.

Если activation не передана, существующий локальный сценарий обёртки сохраняется; это не новый production bypass проверки. В production с переданной activation READY требует успешного результата обеих фаз.

Сохраняются существующие имена событий и причины отказов, в том числе correlation_replay_succeeded означает успех replay(), а не готовность всей локальной фазы. readiness_ready публикуется только при окончательном успехе; entry_admission_rejected по закрытым остаткам публикуется однократно при локальном восстановлении.

## Проверки при приёмке

| Сценарий | Ожидаемый результат |
| --- | --- |
| replay возвращает отказ или бросает исключение | Нет закрытия остатков, чтения active records, Bybit и READY; исходная причина сохранена |
| Закрытие остатков бросает исключение | Нет проверки привязок и READY; локальный результат failed |
| Проверка привязок получает failed local result | Даже при подставном успешном Bybit нет запросов и READY; исходная ошибка сохранена |
| Локальная фаза успешна, биржевая ещё ожидается | READY отсутствует до завершения проверки |
| Биржевая проверка возвращает отказ или бросает | Локальный успех сохранён, execution not ready, причина биржевого отказа сохранена |
| Повтор биржевой проверки успешен | Локальные вызовы и admission events остаются однократными; обе фазы успешны |
| Обе фазы успешны | Порядок replay → cleanup → bindings → READY; один readiness_ready |
| One-way, пустой hedge, несовместимая policy | Прежние результаты и число биржевых запросов |
| Существующие локальные вызовы без activation | Сохранён прежний результат и события |

Проверки используют fake Bybit и управляемые Promise; реальные запросы Bybit не нужны. Обязательны npm test, npm run typecheck, npm run build и diff review границ.

## Risks / Trade-offs

- Возможность вызвать markReady() без локального успеха → обе фазы не владеют readiness; обёртка проверяет сохранённый local result и результат bindings, тест прямого вызова с failed result.
- Повтор cleanup при сетевой ошибке → биржевая функция не имеет зависимости от локального replay/cleanup; тест счётчиков после повторной проверки.
- Изменение событий или one-way/hedge поведения при извлечении кода → регрессии существующих lifecycleEvents и position-mode тестов.

## Порядок ревью и интеграции

Будущий implementation PR 3A основывается на актуальном main, не на PR #51 и не требует промежуточного REST PR #53. Он содержит только выделение фаз и тесты; не переносит новый источник credentials из #53. Это позволяет проверить сохранение нынешней работоспособности независимо от авторизации. Слияние и deploy всё равно требуют отдельного разрешения.

Далее отдельное ревью: 3B — настоящий ограниченный verifier, age/socket и root; 3C — создание observers после авторизации и shutdown; 3D — admission, routes, guards, healthchecks. Если соседние части необходимы для работоспособности, они принимаются по отдельности и сливаются только согласованным совместимым набором. Production verifier с безусловным accepted запрещён.
