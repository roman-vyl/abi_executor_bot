## Context

В main REST, account guards и private stream используют credentials из AbiConfig. replayCorrelationStore() выполняет локальное восстановление, закрытие оставшихся admission intents и существующую проверку привязок. Это рабочий механизм торговой системы, а не часть новой авторизации; самостоятельная переработка replay не требуется.

PR #52 реализует изолированный AuthorizationService. Draft PR #53 использует его узкий интерфейс для REST, но без composition root пока не является работоспособной совокупной версией ABI.

## Goals / Non-Goals

Добавить независимую позднюю авторизацию к существующему ABI. Сначала закончить verifier и доставку, затем отдельно интегрировать их. Не создавать универсальный lifecycle manager, новый recovery-протокол, второй ABI, новый торговый orchestrator или параллельный env-режим. Не переделывать correlation subsystem.

## Decisions

### Один владелец авторизации

AuthorizationService получает verify(candidate) и знает только accepted, rejected и temporary_failure. Подтверждённая пара — замороженная копия двух строковых полей. credentials() доступен только в AUTHORIZED. Одна проверка одновременно; во время неё busy. Temporary failure сохраняет кандидата для retry(), rejected удаляет его. Подтверждённая пара не заменяется повторным authorize().

REST использует Pick<AuthorizationService, "credentials">; одна пара на логический подписанный запрос, timestamp/HMAC на каждую GET-попытку. Нет копии ключей в AbiConfig или fallback. При завершённой интеграции источник обязателен. Публичные market-запросы не требуют credentials.

### Следующий шаг: verifier и защищённая доставка

Verifier — отдельная ограниченная проверка кандидата, не режим рабочего REST-адаптера. Только фиксированные операции чтения, необходимые для проверки credentials, expected UID и требуемых прав; произвольные пути, order writes и публичный обход с accepted исключены. Конкретные Bybit endpoints и классификация ответов сверяются с официальным контрактом и выносятся на отдельное ревью перед Apply этого шага.

Отсутствующий expected UID или неполная проверка прав не дают accepted. Явное несоответствие UID/прав или достоверная ошибка credentials дают rejected. Timeout, сеть, VPN, generic HTTP 403 и нераспознанный ответ дают temporary_failure. Значения ключей и сырой ответ не попадают в диагностику.

Каждая попытка имеет общий deadline и отмену при закрытии. До возврата accepted повторно проверяются deadline/отмена. Поздний сетевой результат не может авторизовать сервис после завершившейся отмены. Сетевой запрос отменяется, таймеры и listeners освобождаются; одного Promise.race недостаточно. Подтверждённые credentials сохраняются при последующих временных сетевых сбоях. Retry сохранённого кандидата явный, без нового пароля и без нового автоматического retry scheduler.

age на Mac расшифровывает файл; после успешного завершения и проверки полной пары команда передаёт ограниченный frame через stdin локального docker exec в Unix socket. Не через argv/env, не через постоянные открытые файлы. Socket 0600, каталог 0700 в tmpfs; лимит размера/времени чтения, проверка структуры полной пары до authorize(). Перед передачей проверяется запрет container swap; гарантий отсутствия swap macOS нет. Cleanup временных буферов — best effort, не обещание уничтожения всех копий в памяти. Без привилегированного контейнера и Docker socket внутри ABI.

Сначала тестируется реальный verifier на подставном транспорте и socket handler на отдельном AuthorizationService. Production startServer и торговый журнал в этом шаге не меняются. Operator-facing авторизация production появляется только вместе с реальным verifier; production fake accepted запрещён.

### Затем отдельная интеграция composition root

```text
age → Unix socket → AuthorizationService ← ограниченный verifier
                            │
                      CredentialsSource
                            │
                    существующий REST
                            │
                  существующие use cases
                            │
                  существующий journal
```

AUTHORIZED фиксируется после проверки credentials/UID/прав независимо от replay. Account API использует авторизацию и свои прежние ограничения безопасности. Для trade-cycle операций дополнительно нужны успешное локальное восстановление и необходимые проверки привязок.

При интеграции сохраняется результат replay + cleanup; биржевая часть откладывается до AUTHORIZED. Ошибка локальной части не может быть скрыта успешной биржевой проверкой. Повтор биржевой проверки не повторяет локальные durable действия. Это минимальная правка существующей последовательности, без отдельной capability replay, универсальных результатов фаз или предварительного рефакторинга журнала. Точный diff рассматривается в ревью интеграции.

Observers создаются после авторизации, а не заранее как постоянные no-op handles. Создаются однократно; используют собственные WS reconnect и REST worker. Backfill и состояние private WS не являются новым условием trading readiness. Наблюдательному REST доступен факт успешного локального восстановления, без зависимости от trading readiness.

При начале shutdown composition root немедленно закрывает новый admission и канал авторизации, отменяет verifier/activation и запрещает поздние переходы в AUTHORIZED/READY. Уже допущенные торговые операции проходят существующий drain; cleanup ресурсов не закрывает используемые ими зависимости преждевременно. Для этого отдельно проверяется существующий shutdown hook, до ожидания server.close().

### Admission и совместимость

Единый механизм допуска использует нужные предикаты категории операции, без глобального смешения авторизации и journal readiness. 503 execution_not_ready возвращается до use case и любых торговых побочных действий. После допуска неопределённые результаты идут по существующему пути, без преобразования в такой 503. Очереди отклонённых команд нет.

Account routes и live guard при интеграции перестают читать ключи из config, но сохраняют dry-run, liveTradingEnabled и запрет Mainnet. Торговые контракты и форматы состояния сохраняются. Runtime #46 различает достоверный отказ и неопределённость без второго reconciliation.

## Risks / Trade-offs

- Промежуточный REST без root неработоспособен для signed calls → draft #53, не сливать до работоспособной серии; env fallback запрещён.
- Смешение авторизации и журнала → verifier/service не импортируют recovery/readiness; интеграционные тесты разрешают account reads при сломанном журнале, но запрещают trade-cycle execution.
- Дубли observers и поздние Promise после shutdown → однократное создание, остановка и проверка отмены после await.
- Компрометация ABI, пользователя Mac или Docker daemon → вне принятой защиты этого этапа; память ABI содержит рабочую пару.

## Migration Plan

Каждый шаг — отдельное ревью и Apply. Начинаем с независимых verifier/доставки, затем интегрируем composition root с минимальными изменениями запуска и допуска. Промежуточные неработоспособные версии в main не сливаем и на действующий Demo не выкатываем. Действующий Demo продолжает работать как раньше.

После готовности совместимого набора — отдельное разрешение на Demo smoke: Deploy → LOCKED → авторизация → READY → торговый цикл → restart → LOCKED. Прежние abi:8787, данные и настройки сохраняются. Перед эксплуатационным переключением и откатом сверяются реальные заявки/позиции; откат использует прежний образ и конфигурацию. Mainnet не включается.
