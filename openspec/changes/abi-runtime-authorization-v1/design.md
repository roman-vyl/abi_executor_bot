## Context

PR #49 реализует age и startup-барьер, PR #103 добавляет интерактивную ветку деплоя. Новая цель отделяет Deploy от авторизации. Исследованы src/app/server.ts, config.ts, lifecycleEvents.ts, exchangeStreamStartup.ts и createExchangeRestReconciler, а в Runtime — entry bridge, _execute_one и UncertainExchangeStateResolver.

## Goals / Non-Goals

Цель — Deploy поднимает весь BBB, оператор авторизует живой ABI в любой момент. Сохраняются существующие хранилища, trading services и reconciliation. Границы объёма заданы в proposal.md. Эта папка является общим планом координации трёх репозиториев, реализация Runtime и bbb_stack выполняется отдельными согласованными PR.

## Decisions

### Минимальная поздняя инициализация

HTTP, SQLite, correlation repository, mutex, расчёт позиции и application services создаются при старте. Защищённая конфигурация допускает risk sizing без ключа до авторизации. Env-based путь сохраняет текущую проверку конфигурации.

Авторизационный контроллер владеет парой и статусом. REST-адаптер получает пару через узкую точку чтения credentials перед подписью. Пара устанавливается целиком, HTTP не может её менять. Это сохраняет ссылки существующих use cases на адаптер. Private WS и наблюдательный REST reconciler создаются после проверки пары, их status/stop доступны через существующие handles. Каждый запускается не более одного раза. Остановка процесса закрывает активные handles и общий adapter.

Local replay выполняется один раз. Биржевая часть текущего replayCorrelationStore, включая assureConfiguredActiveBindings, вызывается при активации отдельно от локального replay и closeLeftoverAdmissionIntents. Сбой биржевой проверки не повторяет локальные изменения. Наблюдательный backfill не входит в барьер READY.

### Авторизация и ошибки связи

Статусы LOCKED → AUTHORIZING → RECOVERING → READY описывают авторизацию и активацию. reason и последняя безопасная ошибка дают диагностику без новых торговых состояний Runtime.

Принятая пара при сетевом сбое остаётся в памяти. Таймаут каждой попытки ограничен, повторные проверки выполняются с backoff и прекращаются при shutdown. Достоверный отказ credentials/прав или несовпадение UID освобождает кандидата и возвращает LOCKED. Сетевой сбой, generic HTTP 403 и неразобранная ошибка оставляют кандидата с диагностикой. После READY обычный сетевой сбой не сбрасывает авторизацию.

Фиксированный ABI_EXPECTED_BYBIT_UID обязателен в защищённом режиме. При авторизации UID сравнивается с authenticated Bybit account identity до использования кандидата в торговых операциях. Реестр аккаунтов не создаётся. Права подтверждаются документированным ответом Bybit, тестовых торговых записей для проверки прав нет.

### Канал управления

age читает пароль в терминале Mac. Команда буферизует весь расшифрованный результат и проверяет exit code и пару. Затем проверяет нужный контейнер и memory.swap.max=0 и через docker exec -i запускает короткий клиент Unix socket. Клиент передаёт ограниченный по размеру кадр в /run/abi-authorization/control.sock. Каталог tmpfs имеет mode 0700, сокет mode 0600 и принадлежит UID ABI. Сокет не монтируется на хост. Привилегированный режим и Docker socket внутри ABI не нужны.

Контроллер сериализует попытки. Конкурирующая попытка получает busy, повтор после READY получает already_authorized. В первой версии смена успешно активированного ключа выполняется рестартом ABI и новой авторизацией. При авторизации недоступного Bybit команда сообщает о сохранённом кандидате, последующая проверка выполняется без нового пароля. Команда status доступна без передачи секрета. Ключи, кадры и ошибки парсинга с исходными данными не логируются. Буферы очищаются в finally, это не обещание уничтожения всех копий в памяти.

### Допуск команды и публичный отказ

После transport validation единый execution gate синхронно проверяет readiness и выдаёт допуск без await между проверкой и его фиксацией. Gate охватывает entry, lookup/recovery, protection, close, entry remainder и существующие account operations, обращающиеся к бирже. Journal API остаётся доступным по локальному хранилищу.

Отказ выдаётся до use case, биржевых запросов, correlation writes и изменения execution state. После допуска команда идёт по прежнему пути до успеха или прежней ошибки. Снижение readiness не может переписать её результат на execution_not_ready. Входные данные не помещаются в очередь, admission token не означает отложенное исполнение. Существующие mutex и shutdown/drain сохраняют свои роли.

503 использует закрытый существующий envelope с error.code=execution_not_ready и безопасным error.message. Дополнительные причины публикуются через execution status, а не произвольное расширение error DTO. Все соответствующие OpenAPI и Runtime codecs обновляются согласованно.

### Локальная доработка Runtime

Добавить typed unavailable в модели/декодеры entry_package_codec, entry_cycle_recovery_codec, open_position_codec и position_management_codec. Entry bridge передаёт определённый отказ отдельно от неоднозначной ошибки.

В _execute_one узкий обработчик этого отказа снимает только pending_entry_recovery, установленный для данной команды. Перед сохранением проверяется идентичность попытки под существующей сериализацией. Для Replace отказ второго APPLY сохраняет уже подтверждённое absent-состояние первого CANCEL. Ранее существующие pending-маркеры не удаляются. Ошибка сохранения не маскируется успешной отменой маркера.

UncertainExchangeStateResolver и worker сохраняют прежний алгоритм. Lookup 503 трактуется как временная недоступность через существующее семейство ошибок, без вывода об отсутствии позиции/ордера. Protection/close 503 не подтверждает выполнение и не очищает прежнюю неопределённость. Нового recovery-протокола нет.

### Деплой и совместимость

Docker health использует /health/live. /health/ready отражает готовность торговли, /health сохраняет прежнюю семантику. /execution/mode показывает authorization state и canExecuteLive=false до READY. Успешная авторизация не снимает Mainnet guard или остальные live guards.

PR #103 возвращается к обычному workflow Deploy Demo для всех сервисов. Исчезает условие пропуска ABI ради сохранения ключа. ABI автоматически стартует после деплоя и сбоя в LOCKED. Restart policy защищённого режима становится unless-stopped. Адрес abi:8787, существующие mount, hedge, risk sizing, abi.json и данные сохраняются.

## Risks / Trade-offs

- Рестарт при открытой позиции оставляет интервал без управления из ABI до авторизации → готовность и статус явно показывают блокировку, операторский runbook описывает действие.
- Потерянный HTTP-ответ остаётся неопределённым даже при вероятном отказе → Runtime использует существующий resolver.
- Кандидат может не пройти проверку из-за длительной сетевой недоступности → сохранён в памяти с backoff и диагностикой.
- Процессы с доступом к Docker daemon, пользователь mcroma и исполняющийся код ABI входят в принятую границу доверия. Linux swap запрещён, paging на уровне macOS полностью не исследован.

## Migration Plan

Реализация разделена на пять этапов в tasks.md. Каждый этап принимается отдельно перед разрешением следующего. Сначала Runtime, затем ABI LOCKED и admission gate, затем доставка пары без разрешения торговли, затем активация Bybit и READY, затем bbb_stack. Промежуточные версии не деплоятся в действующий Demo. PR #49 адаптируется на этапах 2–4, PR #103 на этапе 5.

После отдельного разрешения apply провести Demo интеграцию. Старый startup OpenSpec пометить superseded новым change без архивирования устаревших startup-требований в main specs. Перед эксплуатационным переключением закрепить опубликованные совместимые образы и проверить ожидаемый UID. Mainnet активация требует отдельного изменения.
